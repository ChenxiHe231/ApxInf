## Why this variant, and the two mistakes it is easy to make

The AOT reference kernel (`gdn-prefill-bf16`,
`flashinfer_gdn_bf16_t64_sm110_real3392`) is **full-DV, not dv-split**.

1. **`cake_gdn_prefill_dvsplit_*` is the wrong schedule.** At one chunk it is
   100% bit-equal, so it looks right; at the production 53 chunks it scores
   **42.17%** on `o` and **0.001%** on the final state, with cosine 0.99999 and
   a flat ratio distribution. Only a per-chunk breakdown separates "wrong
   dtype" from "wrong schedule". Splitting DV changes the order in which the
   cross-chunk state contribution is reduced; the AOT kernel does not split it.
2. **`total_tiles = num_seqs * num_v_heads`, not `* 2 * num_v_heads`.** The
   `* 2` is the dv-split value.

Build macros (`HEAD_GROUP_LOG2` and `NUM_O_HEADS_LOG2` are *not* defined in the
source; `IS_GQA`, `THREADS`, `SMEM_TOTAL` are, and are `#undef`'d on the file's
last lines so a wrapper cannot read them after the `#include`):

```
-DHEAD_GROUP_LOG2=1 -DNUM_O_HEADS_LOG2=5 -DIS_GQA=0
--generate-code arch=compute_110a,code=sm_110a
-DNDEBUG
```

i.e. 16 qk heads / 32 v heads, `2^1` v heads per qk head, `2^5 == 32` o heads.
`-arch=sm_110a` alone is wrong: nvcc also emits `compute_110` PTX and ptxas
rejects tcgen05 for the non-`a` target. `--use_fast_math` is deliberately NOT
used; the bit-exactness gate
(`crates/apxinf-cuda/tests/qwen_drive_gdn_prefill_equivalence.rs`) is what
establishes that dropping it is safe here.

Resource fit on Thor, from the vendored source's own constants
(`THREADS=384`, `SMEM_TOTAL=226048`):

```
registers      168 x 384 = 64512  <= 65536
shared memory  226048 + 1024 = 227072 <= 232448   (4.9 KB margin)
```

`__launch_bounds__(384, 1)`, one CTA per SM by design, persistent:
`grid_x = min(SM_count, total_tiles)`.

## `USE_INITIAL_STATE = 0`, and why

This file is the no-initial-state sibling (`USE_INITIAL_STATE 0`,
`STORE_FINAL_STATE 1`), which matches the AOT contract's
`initial_state = false` exactly. Feeding a zeroed state to the
`USE_INITIAL_STATE=1` sibling (`cake_gdn_prefill_initial.cu`) was measured to
be **byte-identical** on both `o` and the state, so a zero state is a valid
equivalent -- it is just 1.5-3.5% more expensive. Use the `=1` file if a decode
continuation path ever needs an incoming state; it is not vendored here because
nothing calls it.

## `APXINF_GDN_LOG_GATE` must stay undefined

The stock kernel takes `gate` as a **linear-space** decay and converts it with

    asm volatile("lg2.approx.ftz.f32 %0, %1;" : "=f"(_log2_N) : "f"(gate_val_N + 1e-10f));

Our pipeline produces `g` in natural-log space, so handing it `exp(g)` for the
kernel to take `lg2` of again looks like a wasteful round trip, and the
alternative patch (`_log2_N = gate_val_N * 1.4426950408889634f`) looks free.
**It is not.** Gate loads are prefetched `NUM_GATE_PIPE_STAGES = 5` deep -- not
4, as the `apxinf-cuda-new` README's analysis of the FP16 variant assumes -- so
at a short sequence the pipeline reads past the end and picks up uninitialized
slots. `lg2(garbage + 1e-10)` collapses whatever it finds into a finite log
that the decay then treats as harmless; a multiply by `log2(e)` *preserves* the
garbage and scales it. Measured state RMS at seq 64: **2.657e26** with the
patch on versus **4.262e-2** off.

That hazard was then re-tested properly for this depth-5 variant, because the
oracle's own padding (`alpha = 1`, `beta = 0` past the sequence) is benign and
re-running the oracle does not exercise the prefetch at all. With the padding
tokens' `gate`/`beta`/`q`/`k`/`v` overwritten with hostile values
(`±1e30`, `-100`, `0`, bf16 `±3.4e38`, `NaN`, `±Inf`), valid-token output
stayed **100% bit-equal** at seq 64/128/3387 with `o nonfinite = 0` and
`state nonfinite = 0` in all nine runs. **Keep that property**: the caller
exponentiates and passes `alpha = exp(g)`.

Worth recording how nearly the gate bug slipped through: the ruined state
pointed the right direction, so **cosine scored 0.999988 on it**. Only a
magnitude assertion caught it. Any comparison written against this kernel must
check magnitudes and bit counts, not just cosine.
